# Agent integration

Building the agent is out of scope for this phase. This records what the
foundation guarantees, what it constrains, and where the sharp edges are, so the
integration work starts from evidence rather than discovery.

---

## What is already true

| Requirement from the brief | Status |
|---|---|
| Separate campaign content from presentation rules | Content lives in template front matter and slot copy; every presentation value comes from `lib/tokens.mjs` via `page.*`. |
| Deterministic HTML, no browser-side execution | Pure Node. Same input, same bytes. Nothing renders or measures at build time. |
| Source and compiled HTML under version control | `build_production/` is committed alongside `src/`. |
| Structured campaign content inserted safely | `mc:edit` regions name every insertion point. |
| Locked vs campaign-editable content distinguished | The layout owns masthead and footer; only components with an `edit` prop are editable. |
| Automated validation before a draft is created | `bin/validate.mjs --json` returns machine-readable findings and a non-zero exit on error. |
| No manual-only techniques | Every asset is generated by `bin/build-assets.mjs`; nothing requires a design tool. |
| Documented limitations | Below. |

## The intended pipeline

```
campaign brief
  → structured content (JSON)
  → write src/templates/<slug>.html front matter + slots
  → maizzle build production          (deterministic)
  → node bin/plaintext.mjs            (deterministic)
  → node bin/validate.mjs --json      (gate: non-zero exit blocks the draft)
  → Mailchimp API: create campaign, set content
  → node bin/validate.mjs --delivered (gate: size and links against real output)
  → leave as a draft for human review
```

**The agent should create drafts, never send.** Nothing in this foundation
prevents sending; the constraint is editorial, and it should be enforced in the
agent, not assumed.

## The API contract

`mc:edit` region names are the contract. Mailchimp's API accepts them directly:

```http
PUT /3.0/campaigns/{campaign_id}/content
{
  "template": {
    "id": <template_id>,
    "sections": {
      "hero_image":  "<img ...>",
      "lead":        "<table>...</table>",
      "cta_section": "<table>...</table>",
      "body":        "<table>...</table>"
    }
  }
}
```

Current region names: `hero_image`, `lead`, `cta_section`, `body`. Renaming one
breaks every campaign and automation built against it. Treat them as a public
interface.

The alternative is posting whole HTML:

```http
PUT /3.0/campaigns/{campaign_id}/content
{ "html": "<!DOCTYPE html>...", "plain_text": "..." }
```

Both are supported from one source. Whole-HTML is simpler for an agent that
generates the entire email; sections are better when a human is expected to edit
afterwards in the builder.

## Validation output

```bash
node bin/validate.mjs --json
```

```json
{
  "report": [
    { "name": "reference",
      "findings": [
        { "level": "error", "check": "contrast",
          "message": "3.96:1 for #6b6b6b on #e2ded5 at 14px (needs 4.5:1)." }
      ] }
  ]
}
```

`level` is `error`, `warn` or `info`. Exit code is non-zero if any error exists.

The twelve checks the brief asked for are all present, plus brand rules:

missing required content · excessive copy length · broken links · missing alt
text · non-HTTPS assets · invalid merge tags · missing footer requirements ·
HTML size · colour contrast · heading order · unsupported elements ·
plain-text completeness · green-band rationing · overline cap · underline at
rest · zero border radius · RTL padding symmetry · double-escaped ampersands ·
unguarded personalisation tags · unbalanced conditional blocks

Each has a self-test in `bin/validate-self-test.mjs` proving it fires.

## Constraints the agent must respect

These are the ones that produce silent, shipped defects rather than build
errors. Everything else is caught by the validator.

1. **Write a plain `&` in hrefs, never `&amp;`.** PostHTML escapes it, so
   `&amp;` becomes `&amp;amp;` and the delivered URL contains a literal
   `&amp;`. *This one is now caught, but only because it shipped once.*

2. **Numeric props are `JSON.parse`d.** `level="1"` arrives as the number `1`,
   so comparisons use `==`. `gap="0"` arrives as falsy `0`, so components check
   `prop === ''` rather than truthiness.

3. **Every component prop needs a default in `config.js`.** A comparison against
   an undefined prop throws inside posthtml-expressions and the entire
   expression renders as an empty string, producing `color:;` with no build
   error and no warning. This is the single nastiest failure mode in the stack.

4. **One campaign is one locale.** Do not attempt to switch language inside an
   email. Generate one template file and one Mailchimp campaign per locale.

5. **Image format must be pinned.** Use `buildEmailImageUrl()` from
   `lib/image-url.mjs`, never the site's `buildPublicImageUrl()`, which bakes in
   `auto=format` and ships AVIF/WebP that classic Outlook cannot render.

6. **Component padding must stay horizontally symmetric**, or RTL breaks. Email
   has no logical properties.

7. **The green band is rationed to one and may not sit above the footer.**

## Known limitations for automation

| Limitation | Impact | Mitigation |
|---|---|---|
| `mc:repeatable` blocks are awkward to address through the API | A repeating list of properties cannot be cleanly filled section-by-section | Generate the whole region's HTML and post it as one section, or post whole HTML |
| Merge tags do not populate in test sends | The agent cannot verify personalisation by sending itself a test | Use the live-merge preview endpoint, or check structurally: the validator already enforces that every contact tag is inside a conditional |
| Mailchimp rewrites links and injects markup after upload | Compiled size and link validity are not conclusive | Re-run `--delivered` against the source pulled back from Mailchimp |
| Link Checker is unavailable for Code Your Own | No built-in broken-link detection on that route | Use the template route, and run `validate:links` regardless |
| Audience merge tags are per-audience | `*|FNAME|*` may simply not exist | Fetch the audience's merge-field list from the API and reconcile with `lib/merge-tags.mjs` before generating |
| The reference photo is a static asset | Not representative of the CMS path | Real campaigns must use `buildEmailImageUrl()`; the fixture is deliberately static so it cannot break |
| Arabic type sizes unreviewed | The 11px overline is likely too small for Arabic | Have a native reader review before the first UAE campaign |
| No rate limiting or retry logic here | Out of scope | Belongs in the agent |

---

## What is deliberately not built

Content structures and component schemas. Defining them before there are real
campaigns to generalise from would fix the wrong abstraction. The primitives in
`src/components/` are the alphabet; the vocabulary comes later, informed by what
the content team actually briefs.
